# ADR-002: 顧客とメンバーの認証アカウント共有

## ステータス

承認済み（改訂: 分離 → 共有に変更）

## コンテキスト

本システムには「顧客」と「テナントメンバー」という2つのユーザー種別がある。それぞれ異なる登録ページ、ログインページ、機能を持つ。

better-auth は単一のユーザーテーブルを使用し、メールアドレスはユニーク制約がある。一方、美容師が別の店舗で顧客として予約する等、同一人物が顧客とメンバー両方の機能を利用するユースケースは現実的に発生する。

## 決定

同一の better-auth ユーザー（同一メールアドレス）で、**Customer エンティティと Member エンティティの両方を持てる**ようにする。

- 1つの better-auth ユーザーに対して、Customer と Member は独立して作成・削除できる
- ユーザー種別の判別はドメインエンティティの存在で行う
  - `customerRepository.findByAuthUserId(authUserId)` → Customer が存在する
  - `memberRepository.findByAuthUserId(authUserId)` → Member（テナントメンバーシップ）が存在する
  - `user.role === "admin"` → プラットフォーム管理者
- ログイン後、対応するドメインエンティティが存在しない場合はプロフィール作成フローに誘導する
- 顧客の停止は **ドメインレベル**（Customer.status）で管理し、better-auth の BAN は使用しない
- auth ユーザーの削除は、Customer と Member の両方が存在しなくなった場合にのみ実行する

## 検討した代替案

### 1. 同一メールでの重複登録を禁止（旧 ADR-002）

同一メールアドレスで顧客とメンバーの両方に登録できないようにする。

**不採用理由**: 美容師が顧客として他店を予約する等、同一人物が両方の機能を利用する現実的なユースケースを排除してしまう。

### 2. 別々の better-auth インスタンス

顧客用とメンバー用で別々の better-auth インスタンスを立て、別々のユーザーテーブルを使用する。

**不採用理由**: better-auth は単一インスタンスでの利用を前提に設計されている。複数インスタンスの管理はセッション管理やミドルウェアが複雑になる。

### 3. better-auth の role フィールドでユーザー種別を管理

admin プラグインの `role` フィールドに "customer" / "member" / "admin" を設定する。

**不採用理由**: admin プラグインの `role` は管理者権限の判定に使用される。ユーザー種別はドメイン層の関心事であり、認証基盤が管理すべきではない。また、role は単一値であり、「顧客かつメンバー」を表現できない。

## 影響

- 同一メールアドレスで顧客とメンバーの両方に登録可能
- ログインは共通（同一セッション）。どちらのコンテキストで操作するかはアクセスする URL で決まる
- 顧客の停止（suspendCustomer）は Customer.status を "suspended" にするのみ。better-auth の BAN は使用しない。これにより、顧客を停止してもメンバーとしてのアクセスは維持される
- better-auth の BAN はプラットフォームレベルのブロック（全アクセス遮断）に限定する
- アカウント削除時、Customer と Member の両方が存在しなくなった場合にのみ auth ユーザーを削除する。一方のみ削除した場合は auth ユーザーは維持される
- 登録ページで「メールアドレスが既に登録済み」の場合、ログインを促し、ログイン後にドメインエンティティを作成するフローに誘導する
