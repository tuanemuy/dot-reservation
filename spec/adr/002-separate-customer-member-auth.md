# ADR-002: 顧客とメンバーの認証アカウント分離

## ステータス

承認済み

## コンテキスト

本システムには「顧客」と「テナントメンバー」という2つのユーザー種別がある。それぞれ異なる登録ページ、ログインページ、機能を持つ。

better-auth は単一のユーザーテーブルを使用し、メールアドレスはユニーク制約がある。同一メールアドレスで複数のアカウントを作成することはできない。

## 決定

顧客とメンバーは**同一の better-auth ユーザーテーブル**を共有するが、**同一メールアドレスでの重複登録は許可しない**。

- 顧客登録時、メールアドレスが既に使用されていればエラーとする
- メンバー登録時、メールアドレスが既に使用されていればエラーとする
- ユーザー種別の判別は better-auth のロールではなく、**ドメインエンティティの存在**で行う
  - Customer エンティティが存在する → 顧客
  - Member エンティティ（の元となるアカウント情報）が存在する → メンバー
  - user.role === "admin" → プラットフォーム管理者
- ログインページでの認証後、対応するドメインエンティティの存在を確認し、存在しない場合はエラーメッセージを表示する

## 検討した代替案

### 1. 同一メールで顧客・メンバー両方に登録可能

同一の better-auth ユーザーに対して、Customer エンティティと Member エンティティの両方を作成可能にする。

**不採用理由**: 顧客とメンバーは異なるユーザー体験を持ち、セッション管理が複雑になる。ログイン時にどちらのコンテキストで操作するか選択が必要になり、UX が煩雑になる。将来的に必要になった場合は拡張可能。

### 2. 別々の better-auth インスタンス

顧客用とメンバー用で別々の better-auth インスタンスを立て、別々のユーザーテーブルを使用する。

**不採用理由**: better-auth は単一インスタンスでの利用を前提に設計されている。複数インスタンスの管理はセッション管理やミドルウェアが複雑になる。

### 3. better-auth の role フィールドでユーザー種別を管理

admin プラグインの `role` フィールドに "customer" / "member" / "admin" を設定する。

**不採用理由**: admin プラグインの `role` は管理者権限の判定に使用される。"customer" や "member" を role として扱うと admin プラグインの意図と合わない。ユーザー種別はドメイン層の関心事であり、認証基盤が管理すべきではない。

## 影響

- 同一メールアドレスで顧客とメンバーの両方に登録することはできない
- ログイン認証は better-auth が処理し、ユーザー種別の判定はアプリケーション層で行う
- 顧客ログインページでメンバーアカウントのメールアドレスでログインした場合、セッションは作成されるが、Customer エンティティが見つからずエラーとなる
- 将来的に同一メールでの複数種別対応が必要になった場合、ドメインエンティティの作成ロジックを変更するだけで対応可能（better-auth 側の変更は不要）
